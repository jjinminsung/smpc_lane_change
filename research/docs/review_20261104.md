## Ranked findings (most severe first)

### 1. [C++, critical] Tree evaluation takes 1.1–1.5 s per SMPC tick. The budget is 50 ms.
`src/smpc_decision_node.cpp:4109-4209` (`treeResponse`), `:4252` (`treeEvaluate`), `:4422` (`treeSelect`), `:4537` / `:4786` (calls in `timerCallback`)

**What is wrong**

- `treeResponse` calls `LanePath::projectExtended` for each of the K = 40 root poses. That function is a linear scan over the whole lane polyline (`include/smpc_lane_change/lane_path.hpp:109`).
  - It runs for every branch (≤ 6) × every non-continue response (4) × every root (CHANGE_NOW + up to ~19 future candidates).
  - The projection does not depend on the branch or the response.
  - The `|d_b| ≤ 1.75` rejection (`:4155`) is evaluated only after all 40 projections.
- Measured with the real CSVs (src/tgt point counts 12187/4040, 4040/4180, 4180/11077), 6 branches, 19 roots:

  | lane pair | `treeEvaluate` ×19 per tick | `treeMonitorReturn` per tick |
  |---|---|---|
  | 0→1 | 1335 ms | 87 ms |
  | 1→2 | 1059 ms | 77 ms |
  | 2→3 | 1510 ms | 119 ms |

  The machine had load ≈ 30, so halve these numbers for an idle PC. They are still 10–15× over budget.
- `treeSelect` also runs during an active lane change, because the SMPC keeps evaluating the held pair. So the monitor that replaces `rear_abort` is evaluated about once per second, not at 20 Hz.
- The baseline future-candidate loop (`:4716-4750`) also still runs, and its results are thrown away.
- The Python simulator evaluates instantly. None of the sim results include this latency.

**Failure scenario (MORAI / real car).** With `tree_planner_enabled`, the following all happen at about 1 Hz:
- `/smpc/decision`, `/smpc/tree_abort` and the behaviour request.
- The supervisor needs 3 consecutive CHANGE_LEFT messages, so acceptance is about 3 s after the gap was judged safe. The targets used for that judgement are up to about 1 s old.
- The single-threaded spinner also blocks `/odom` and `/smpc/targets` callbacks while it computes.

**Suggested fix**
- Project each root once (or carry s, d from `buildEgoTrajectory`).
- Do the `allowed` check before the per-step work.
- Use a local segment search (warm start from the previous index).
- Skip `treeSelect` and the baseline candidate loop while `lc_status_.active`.
- Add a timing assertion to the harness, for example `< 20 ms` at 6 branches × 20 roots on lane 3.

### 2. [Claim / attribution, high] The 0 collisions come from the execution-time monitor, not from contingency planning at decision time. A baseline with the same monitor matches or beats the tree.
`research/sim/smpc_sim/world.py:87-88,188-191`, `research/sim/smpc_sim/supervisor.py:90-138`, `research/sim/smpc_sim/tree.py:362-421`

**What is wrong.** The README compares "tree + gate removal (0 % collisions)" with "baseline, gates removed (6.5 %)". These two arms differ in three things at once:
- (a) the decision rule;
- (b) the in-execution abort: the tree monitor vs `rear_abort`;
- (c) the probability table (see #4).

`rear_abort` only reacts to target-lane vehicles **behind** the ego. `front_ok` is only consulted when a rear threat exists.

**What I found**

- **All 13 `baseline_nogate` collisions are front collisions.** The ego rear-ends a slower target-lane NPC ahead, mid-manoeuvre: ego y 1.8–2.9 m in a 0→1 change, NPC ahead at 0–16 m/s, ego at 11–22 m/s. Seeds: 2003, 2005, 2018, 2021, 2031, 2038, 2069, 2124, 2125, 2136, 2154, 2155, 2166.
  - None is the hazard the tree's branches are built for (rear vehicle accelerates).
  - The cause is the ACC's target_front authority during a change: none at |d_t| > 2.7, soft 1.5 m/s² down to 0.75. The F7 prediction instead assumes a 4 m/s² reaction after 0.5 s.
- **The tree approves the same merges.** Seed 2005: both arms accept at t = 1.65 s. The tree monitor then returns at 2.5 s. `rear_abort` never fires because the threat is in front.
- Ablations (paired, seeds 2000–2199, snapshot code):

  | variant | success | collision | merge median | Δ vs baseline (s, 95 % CI) |
  |---|---|---|---|---|
  | tree_gt_nogate (README) | 92.0 % | 0 % | 29.8 s | −14.9 [−19.3, −10.2] |
  | **tree_gt_nogate, monitor off** (`rear_abort` instead) | 82.0 % | **5.0 %** (10/200, all front collisions, 5 on the same seeds as `baseline_nogate`) | 29.2 s | −5.0 [−10.5, +0.4] |
  | **baseline, G3/G5 off, GT table, + tree monitor** (no tree at decision) | **96.5 %** | **0 %** | 32.1 s | −15.7 [−20.0, −11.7] |
  | tree_gt_nogate − (baseline + tree monitor), paired | | | | **+0.7 [−2.0, +3.3]** (no difference) |

**Failure scenario.** The evidence supports "gate removal is safe *with a front-aware execution monitor*". It does not support "the scenario tree makes gate removal safe". On MORAI, `rear_abort` is disabled, and the only safety layer left is the monitor, which runs at about 1 Hz (#1).
- A 1 s monitor period does not create collisions in the sim (`monlag1.0`: 0 %, −17.2 s).
- It does raise the number of episodes with 2-D box separation under 0.5 m from 0 to 7, of which 6 are side by side with under 0.5 m lateral clearance.
- The sim does not model the matching delay in decisions and acceptance.

**Suggested fix**
- Report the 2×2 ablation (decision: baseline / tree × execution: `rear_abort` / monitor) with the same probability table.
- Either credit the gain to the monitor, or show a decision-side benefit on top of "baseline + monitor".

### 3. [Sim fairness, high] The ACC port applies the SMPC behaviour cap **before** the lane-end logic and the merge-keep-rolling floor. C++ applies it after.
`research/sim/smpc_sim/acc.py:104-121` vs `:146-150`; C++ `src/acc_speed_planner_node.cpp:1253-1298`, which says: "This is deliberately after the merge rolling floor. A selected YIELD/HOLD candidate must be able to lower speed…"

**What is wrong**
- In the port, the 11.1 m/s `merge_keep_rolling` floor overrides any YIELD/HOLD/ACCEL cap below 11.1 m/s whenever lane-end pressure is on, which is always the case in lanes 0–2 within 400 m.
- A YIELD-ing ego therefore cannot slow down to open a gap.
- An active YIELD/HOLD request does not arm the lane-end wait (correct in both versions). So the ego can roll off the CSV end at 11.1 m/s.
- `external` is also computed before the lane-end labels (`acc.py:105`), unlike C++ (`:1263`).

**Failure scenario.** Baseline seed 2007:
- From t = 4.5 s the baseline requests `yield(-0.25)@0.4`, but the speed stays at 11–12 m/s.
- It drives past the end of lane 0 at t = 9.45 s. This is counted as a failure and censored at 120 s.
- With the C++ order (patched in the scratchpad), the same seed merges at 26.1 s.

12 of 200 baseline episodes end like this ("offroad", no collision). Only 3 tree_gt_nogate episodes do.

| variant | success | offroad | Δ vs baseline |
|---|---|---|---|
| baseline + C++ ACC order | 93.5 % | 6 | −2.3 s [−5.3, +0.3] |
| tree_gt_nogate + C++ ACC order | 93.5 % | 2 | −15.5 s |
| **tree vs baseline, both with C++ order** | | | **−13.2 s [−17.2, −9.5]** (README: −14.9) |

The headline result survives, but about 1.7 s of it, and part of the baseline's failure count, is this port bug.

**Suggested fix.** Move the request-cap block after the merge floor, as in C++. Recompute `external` after the lane-end block. Add an ACC port test against the C++ node.

### 4. [Claim, high] The two arms use different probability tables, and the same-table tree result is not reported.
`research/sim/smpc_sim/tree.py:63-66`, `research/sim/run_batch.py:20-46`, `research/README.md` result table

**What is wrong**
- Both README tree rows use `GT_REAR_TABLE` ([0.006, 0.007, 0.079, 0.275, 0.672], min 0). Both baseline rows use the yaml table ([0.11, 0.15, 0.28, 0.30, 0.31], min 0.05). The p(rear accelerates | not accelerating) is 0.007 vs 0.15.
- The stored `sim_tree_n200.json` (tree, yaml table, gates kept) is omitted from the README: 82 % success, **+8.9 s [+4.9, +12.7] worse** than the baseline.
- `run_batch.py` has no `baseline_gt_nogate` arm.
- `baseline_gt` ≈ `baseline` (−0.3 s), so the gated comparison is not inflated. The gate-removed comparison mixes tables.
  - I ran `baseline + GT + no gates`: 7.0 % collisions, −7.4 s.
- The MORAI launch (`research_morai.launch`, `rear_accel_table` default `gt`) uses the same table for both arms. The sim README does not.

**Failure scenario.** A reader concludes the tree helps. With the baseline's own table it is significantly worse, and every benefit depends on a table fitted to 12.5 m / 5 s events on MORAI GT. That table has not been validated against the simulator's NPC model.

**Suggested fix.** Report every arm with both tables. Add `baseline_gt_nogate` to `run_batch.py`. State which table each row uses.

### 5. [C++, high] In tree mode, no WAIT_FOR_GAP is sent when the tree rejects but the baseline's `change_feasible` is true. The lane-end hold is then not armed.
`src/smpc_decision_node.cpp:4786-4807`, `:4934` (`if (desire_change && !change_feasible)`), `:4968`

**What is wrong**
- With `tree_planner_enabled`:
  - `request_change = desire && tree_change`
  - `have_future_candidate` comes from the tree.
- The WAIT branch is still guarded by the **baseline** `change_feasible`.
- If the baseline gates pass but the tree finds no feasible root, control falls through to the final `publishKeep` / `publishBehaviorOutputs(keep_candidate…)`. That publishes action KEEP with `active = false`.
  - For example: front-brake branch with p = max(p_cf, p_tf), both fronts braking together, or `nominal_clear` failing.
- The ACC's `mergeWaitStopRequired()` (`acc_speed_planner_node.cpp:1010-1018`) then only holds if the target front blocks within 11 m.
- The Python tree (`tree.py:350-353`) always sends WAIT in this case, so the sim cannot show the problem.

**Failure scenario**
- Urgent zone of lane 1 or 2, target front farther than 11 m, tree infeasible because of the current_front brake probability.
- The ACC applies the 11.1 m/s merge-keep-rolling floor instead of stopping at the 25 m holding line.
- The ego reaches the CSV end.

**Suggested fix.** In tree mode use `if (desire_change && !request_change && !have_future_candidate)` for the WAIT branch. Use the tree's own reason string.

### 6. [Logic, medium-high] Decision and monitor use different ego models, so the tree approves merges and aborts them in the same tick.
`research/sim/smpc_sim/tree.py:362-421` vs `:232-359`; C++ `:4338-4419` vs `:4422`

**What is wrong**

| | lateral motion | longitudinal law | threshold |
|---|---|---|---|
| `decide` | CHANGE_NOW root: starts at τ_m = 0.6 s, D = 1.04·T(v) | blendStage from t_sw | ε |
| `monitor` "go" root | linear from τ = 0.2 s over T_rem = T(v)·d/W | blendStage with t_sw = 0 | 2ε |

**Evidence**
- In stored `tree_gt_nogate`, 39 of 145 `tree_return` aborts happen in the **same tick** as the accept. 49 happen within 0.5 s.
- Seed 2054, t = 15.15 s: `decide` gives CHANGE_NOW, all-continue feasible. The monitor in the same tick returns.
- There is a related non-causal case. When the rear is already accelerating (`already`, `tree.py:85-90`, C++ `:4081-4089`), `t_b = 0`.
  - The plan may therefore be "change now and, in the rear branch, return at t = 0+". That treats the future mode as known at t = 0.
  - It ignores the observed acceleration at no risk cost.
  - It happened in 3 of 581 approval ticks over 40 episodes, so it is rare.

**Failure scenario (C++).** `/path_number` goes target → source within about 50 ms, or within one slow tick (#1). The waypoint system starts a blend and reverses it. A 3 s cooldown is spent each time.

**Suggested fix**
- Build the monitor's "go" root with the same `buildEgoTrajectory` model, shifted by elapsed time. Or reject a root in `decide` if the monitor would return at t = 0.
- For revealed branches use `t_b ≥ t_sw` (0.55 s) plus the detection delay, not 0.

### 7. [C++ vs Python, medium-high] Near standstill the C++ monitor uses a different "go" speed law than the Python reference.
C++ `src/smpc_decision_node.cpp:4365-4372` vs Python `tree.py:390-391` → `rollouts.py:115-142`

**What is wrong**
- Python `blend_stage_rollout` switches to launch mode when v0 < 1.0: V1 = max(pre_cap, cap_conn[target]) and a_up = 4.0.
- C++ `treeMonitorReturn` hard-codes `ref = pre_cap` and 2.4 m/s².
- I swept 48 cases: v0 ∈ {0, 0.5, 3, 8}, rear gap ∈ {25, 40, 60, 80} m at 13.9 m/s, d_t ∈ {−3.2, −2.6, −2.0}. There were **6 disagreements, all at v0 < 1**: rear gap 40 m, C++ returns, Python continues.
- In C++, `pre_cap` at the holding line is the ACC target (≈ 0 when the change is accepted). So C++ predicts no forward motion at all and returns even more often.
- The tests never exercise this: `make_scenario` draws v0 ∈ [5, 25].

**Failure scenario.** The tree's sim gain comes largely from lane-end standstill merges (lane-end stops 0.95 → 0.60 per episode). On MORAI those launches will be aborted far more often than the sim predicts.

**Suggested fix.** Port the launch branch, or call the existing `blendStageRollout` in C++. Add v0 < 1 cases to `test_tree_vs_cpp.py`. Feed `last_acc_target` instead of `None`.

### 8. [Model, medium] The tree plans with responses the stack never commands, and with a return 2–3× faster than the simulated plant.

**Responses** (`tree.py:119-141`, C++ `:4166-4186`)
- `continue+accel` (+1.5 m/s² up to mission speed), `return+decel` (−1.5 m/s²) and `brake` (−3 m/s² from 0.3 s) are counted as risk reductions.
- Nothing commands them:
  - The ACC ignores SMPC requests during an active change.
  - After an abort the ACC simply resumes.
  - The ACC has no target_front authority at |d_t| > 2.7 and 1.5 m/s² soft authority until 0.75, so `brake` and F7 are not executed early in the manoeuvre.
  - The world only executes plain `return`.

**Return speed**
- The tree's return is linear, `max(0.8, 3.1·Δd/3.5)` s.
- The plant (`plant.py:249-260`) replays the S-shaped progress curve scaled by √frac, starting from zero lateral speed.
- Time to get back within 0.45 m:

  | departed | tree model | plant |
  |---|---|---|
  | 1.0 m | 0.49 s | 1.59 s |
  | 1.75 m | 1.15 s | 2.66 s |

- The plant also cancels the ego's lateral velocity instantly at abort, with no overshoot toward the target. That is optimistic for the arm that aborts most (tree_gt_nogate 0.72 aborts/episode vs baseline 0.12).

**Failure scenario.** The step risk the tree certifies (≤ ε) is computed for an ego that escapes faster than either the plant or the real car.

**Suggested fix.**
- Allow only responses the execution layer actually performs.
- If `continue+accel` or `brake` are kept, add an ACC command for them.
- Fit the return model to the plant (or to M2 data with the departure distance).
- Add lateral carry-over at abort in the plant.

**Measured.** Banning `continue+accel` and `return+decel` (`norealize`) gives 89.5 % success and a 34.6 s median. That is **+4.8 s [+2.2, +7.6]** slower than tree_gt_nogate. About a third of the tree's gain therefore rests on responses nobody executes.

### 9. [Sim realism, medium] NPCs yield to the ego early, hard and without delay.
`research/sim/smpc_sim/world.py:124-143`, `npc.py:106-118` (`max_brake = 6.0`)

**What is wrong.** An NPC treats the ego as its leader as soon as the ego's box enters its lane by 0.3 m. It brakes with IDM at up to 6 m/s² and zero reaction time. The SMPC prediction assumes constant speed for the rear vehicle, so that part is pessimistic. Execution, however, is cushioned. This matters most for the arm that accepts the tightest rear gaps.

**Measured sensitivity**
- `npc1`: NPC reacts only after 1.0 m of intrusion and brakes at most 4 m/s². Both arms still have 0 collisions, and the tree advantage holds (−14.0 s [−18.5, −9.5]). The 2-D separation p05 of the tree arm drops from 1.42 to 1.06 m.
- `npcb`: NPCs completely blind to the ego. This is degenerate, because NPCs then also rear-end the ego inside its own lane. Collisions are 31 % for the tree and 46.5 % for the baseline.
- So the 0 % is **not** an artefact of the 0.3 m / 6 m/s² setting. It does assume the ego is seen once it is about 1 m into the lane. I did not test a reaction delay; it is worth adding.

**Suggested fix.** Calibrate the NPC response to the ego from MORAI bags: intrusion at first deceleration, delay, peak decel. Report results under that calibration and under a pessimistic setting.

Severity: medium → low after the measurement.

### 10. [C++, medium] The supervisor's `treeAbortCallback` aborts on one message, with no freshness, heartbeat or debounce, and `rear_abort` is switched off completely.
`src/lane_change_supervisor_node.cpp:69-70,123-126,893-909`

**What is wrong**
- A single `true` aborts. `rear_abort` needed 3 counts / 0.3 s unless it was an emergency.
- `std_msgs/Bool` carries no stamp and no lane pair. Pair and |d_t| are taken from `latest_targets_`, not from the state the SMPC used.
- If the SMPC stalls (#1), crashes, or `tree_monitor_enabled = false` while `tree_abort_enabled = true` (the defaults are coupled only in the launch file), there is **no** abort path at all.
- On the perception side, `revealed` triggers when `filtered_accel ≥ 0.5` on the EMA. One noisy LiDAR sample can trigger an abort.

**Suggested fix**
- Publish a stamped message carrying the lane pair and `d_t`.
- Require N consecutive messages or a time window, except for an explicit emergency flag.
- Keep `rear_abort` as a fallback when the tree message is older than about 0.2 s.

### 11. [C++, medium] The tree path drops several fail-closed checks.
- `treeStepRisk` skips invalid TV samples (`:4241`, `if (!tv.valid) continue;`). `evaluateTrajectory` makes the whole candidate invalid (`target_prediction_invalid_before_lane_end`).
  - Example: a vehicle on a lane id with no CSV (`laneFor` is null), or more than 100 m before the CSV start. It contributes zero risk in the tree and blocks in the baseline. The Python port ignores `invalid` too (`tree.py:166`).
- `nominal_clear` (`:4276`) ignores NaN/−inf clearances. `clearanceSafe` fails closed on them.
- With `tree_keep_gates = false` the CHANGE_NOW root does not require `change_eval.valid` (G2) (`:4455`).
- The pass-gap entry clearance (`target_front_gap ≥ 2.0` while passing) goes away with G3. That clearance was added after lc_gt merges came within 0.7–1.56 m of a passer.
  - Only the tree's probability then protects that case.
  - The sim's metrics would not show a 0.7 m side-by-side near miss (see #13).

**Suggested fix.** Keep G2 and an explicit "no TV prediction invalid" check. Make `nominal_clear` fail closed. Keep the pass-entry clearance as hard safety.

### 12. [target_selector (c), medium for MORAI GT runs] The committed offset patch translates the position only.
`src/target_selector_node.cpp:41-42,1021-1025` @4b61def, `config/target_selector.yaml:8-10`

- **Heading.** `npc.heading` is used unchanged. The repo's own UTM converter applies −1.347° (`morai_udp_bridge/object_info.py: to_map`).
  - Velocity is vehicle-local and is rotated by this yaw. That gives a spurious v_lat ≈ 0.024·v (0.6 m/s at 25 m/s).
  - The box is also rotated by 1.35°.
- **Reference point.** Per the author's later gtcheck, `npc.position` is the rear axle, but it is treated as the box centre. Every NPC therefore appears 1.25 m behind its true position.
  - Rear gaps are **overestimated** by 1.25 m (the unsafe direction).
  - This matters most when the deterministic margins are removed.
- **Time.** No ego/object stamp alignment.
- The offsets live in the shared yaml, not in the launch file. Any `target_source:=object_topic` run, including the MORAI "baseline", now behaves differently from dd1cf54.
- If `competition.launch ground_truth:=true` is ever combined with this, `/Object_topic` is already UTM and the offset is applied twice. The selector then sees no vehicles.
- The uncommitted WIP (heading offset −1.365°, 1.25 m reference shift, ego extrapolation) addresses all three. Only the commit is reviewed here.

**Suggested fix.** Commit the WIP. Move the offsets into `research_morai.launch`. Assert that a published UTM `/Object_topic` is not offset again, for example by checking the distance of the first NPC to the lane set.

### 13. [Metrics, low-medium] No lateral near-miss metric; "offroad" is not counted as a safety event.
`research/sim/smpc_sim/world.py:211-224`, `:247-248`

- `min_gap` only looks at vehicles with lateral offset < half-widths + 0.3 m. Side-by-side passes with 0.3–1 m of lateral clearance are invisible.
- An ego that drives past the CSV end counts as a failure, not as a collision or violation.
- I added a 2-D box-separation metric (scratchpad `variants.py: patch_sep`): min over the episode of max(longitudinal gap, lateral gap), plus a count of episodes with a side-by-side lateral clearance under 0.5 m.
  - The median is 1.60 m for every arm. That is simply two cars in adjacent lanes (3.5 − 1.9).
  - The headline arm is clean: tree_gt_nogate has 1 episode below 1.0 m and none below 0.5 m. The baseline has none.
  - With a 1 s monitor period (`monlag1.0`, the C++ rate from #1), 7 episodes fall below 0.5 m and 6 have a side-by-side clearance under 0.5 m. None of these show up as a collision.
  - With the monitor off, 12 episodes fall below 0.5 m.

**Suggested fix.** Add both metrics to `EpisodeResult`, and count CSV-end overruns as violations.

### 14. [Sim, low] Pairing breaks after the first divergence.
`world.py:75,111-122`, `npc.py:87-103`

- One `rng` drives spawning and every NPC's acceleration episodes.
- The number of draws depends on how many NPCs are alive, and the spawn checks depend on the ego's position (`world.py:105`).
- So as soon as two planners behave differently, the rest of the traffic differs too. The seeds are matched, but common random numbers hold only up to the first divergence, and the paired CI is wider than it needs to be.

**Suggested fix.** Give each lane's spawner and each NPC its own `Generator(seed, uid)`.

### 15. [Minor C++/Python inconsistencies]
- Python `monitor` builds `vehicles` without de-duplication (`tree.py:398`). If target_front == target_rear (an overlapping passer), that risk is counted twice. C++ de-duplicates.
- C++ tree `desire` is the baseline's cost-based desire. Python tree desire is only `endpoint or current_blocked` (`tree.py:299`).
- `v_b` for t_b < 0.2 interpolates from `v[0]` (the speed at 0.2 s), not `ego_speed_mps_` (`:4151`, `tree.py:115`).
- Tree mode clears the 0.6 s YIELD confirmation on every tick (`:4794`; Python does the same). That guard was a perception-robustness measure ("a single association frame must not create a brake pulse"). The lexicographic HOLD > YIELD order is also dropped.
- `TreeBranch` rear mode never sets `max_speed_mps`. This is fine while `rear_accel_max_speed_enabled: false`, but it diverges silently if that is switched on.
- `research_morai.launch` makes the baseline use the GT table, so MORAI baseline runs are not dd1cf54 behaviour. This is documented, but it should be noted when older runs are compared.

### 16. Tests: what they do not cover (`research/sim/tests`)
- `treeSelect`, the `timerCallback` integration and output messages (WAIT / request cap / reason), and the supervisor `treeAbortCallback`. Findings #5, #6 and #10 live in this untested code.
- Equivalence with dd1cf54 when everything is off. A replay of a bag through both binaries, diffing `/smpc/decision` and `/smpc/behavior_request`, would settle (a) for good.
- Real `buildEgoTrajectory` roots: BLEND/CONNECTOR, the lane-end step, truncated roots shorter than K. The test roots are synthetic, full length and straight.
